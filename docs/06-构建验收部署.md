## 规则 30 · embed-sheet 卡的是 base64 体积，不是 PNG 体积

- **机制**：embed-sheet 把 PNG 读成 base64 data URL 写进 `src/sheet.js`（embed-sheet.mjs:54 拼 `data:image/png;base64,`、:110 写入 `var SHEET = {meta, dataUrl, embedded:true, pngBytes}`），硬限卡的是 **data URL 的 UTF-8 字节数**（:55-56：`Buffer.byteLength(dataUrl)` 超 `HARD_BYTES` 即 die，报错原文「base64 内嵌体积 X MB 超过硬上限，请降低 cell 尺寸或减少帧数」）。base64 ≈ PNG×1.34（4/3 编码膨胀），所以「2.66MB 的 PNG 被 3.2MB 硬限拒绝」不是 bug，是它的 base64 已达 3.55MB（docs/08:18 事故 #12 原文记录了这次「人懵了」）。
- **硬限现状与历史**：`WARN_BYTES = 1.4MB`（:18，源头是 dsh-pet-bg/DESIGN.md:72「若 base64 超过 1.4MB 则改走『设置面板里填精灵图 URL』的降级路径」）；`HARD_BYTES = 4.0MB`（:22）。:19-21 注释原文完整记录了原值与上调原因：「硬限原值 3.2MB：bg9 162 帧 112×150 图集 PNG 2.43MB → base64 3.24MB 恰好越线。client.js 3.6MB 在本地刷新场景可用（母代理已批准提高硬限），上调至 4.0MB。素材再膨胀时先降格子（不低于 100×136）再考虑动这里。」
- **当年那次取舍**（2.66MB PNG → 3.55MB base64 被 3.2MB 硬限拒绝时）只有两条出路：
  - a) **降格子**：100×136 ⇒ PNG 2.21MB ⇒ base64 2.95MB，可过。该配置真实存在过：`qanimal/pack162.py:33`（`CELL_W, CELL_H = 100, 136`）；:21 注释同时把 100×136 定为降格子的下限。
  - b) **提高硬限**：代价是 client.js 膨胀 **2.36MB→3.51MB**、首屏变慢（client.js 每次内容变更后的首次加载都要整包下载+解析+执行；:57 的警告文案也明说「client.js 会随之变大（仍可运行）」）。
  - 实际走了「先重打包瘦身、再上调硬限」：162 格 @112×150 第一版 PNG 实测 2,791,382 B（=2.66MB，base64 3,721,844 B = 3.55MB；物理证据 `backup-20260912-2217\petwork-out\spritesheet.png`，随附 pet.json 实读 cell=112×150、8×21、162 帧）被拒；瘦身后 2,548,445 B（=2.43MB→base64 3.24MB）仍越 3.2 ⇒ 硬限上调 4.0MB 放行。

## 规则 31 · assemble：顺序即依赖方向，装配完必须自证语法

## 规则 32 · headless 浏览器验收在沙箱里跑不了 ⇒ 假 DOM 冒烟是验收门槛

- **现象**：`msedge --headless` 即崩——`FATAL mojo platform_channel.cc:183 Check failed (0x5)`，或进程级 status `0x80000003`、stdout 全 null；**两个独立会话都复现**（tools/smoke.mjs:3-5 头注释原文；docs/08:19 事故 #13 同文）。根因：沙箱禁止子进程打开命名管道，Chromium 的 mojo IPC 依赖命名管道 ⇒ 浏览器进程必死；**这是环境边界，不是浏览器或脚本的 bug**（docs/08:19 根因列）。沙箱时代还试过两条绕行（`--user-data-dir` 钉进工作区、用 .cmd 文件包命令躲开引号重排，verify.mjs:278-284 注释记录了各自的死法：user-data-dir 落在重定向临时目录会「status 1 且无任何提示」），都救不了 mojo。历史上非沙箱会话 headless 是跑通过的：verify.mjs --run 实测 60 PASS / 0 FAIL（dsh-pet-bg/README.md:130）。

## 规则 35 · 动手前必备份：`backup-<yyyymmdd-hhmm>\`，一条复制命令可回滚
