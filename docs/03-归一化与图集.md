## 0. 为什么需要归一化：「一会儿大一会儿小」（规则 14）

- **现象**：桌宠播放动画或切换状态时角色忽大忽小（真实踩坑，用户原话「一会儿大一会儿小」）。
- **根因**：**逐帧紧裁是错的**。紧裁 ⇒ 每帧各自算 bbox ⇒ 每帧各自算缩放。两层错误叠加：
  1. 各组角色在源图里画得本来就不一样大：实测 walk 组内容高 174~190px、sleep 组只有 104~112px，
     切状态就会突然变大变小（`qanimal/import3.cjs:85` 注释原文）；
  2. 即使同一组内，逐帧独立缩放会把「跳跃的上移、走路的重心起伏」当成「角色变大了」给归一化吃掉
     （`petwork/tools/sprites.mjs:761-763` 注释原文，说明 build 路线每帧独立缩放的错误），
     帧间产生呼吸式缩放抖动。
- **修法**：两头堵。
  - 素材侧：抠图输出**保留原始画布尺寸，只改 alpha，不裁剪**——「这样同组帧的几何完全一致，
    后面拼图集成一个统一裁剪框时不会忽大忽小」（`qanimal/cutall.py:21-22` 注释原文）；
  - 打包侧：组内共用一个缩放 + 一个裁切框 + 一个落点（见第 1 节）。
    `import3.cjs` 的文件头就是这次修复的记录：「修复：紧裁导致帧尺寸不一 → 忽大忽小」（`qanimal/import3.cjs:1`）。
- **实测数字**：修复后按常量目标高 246px 统一归一（`import3.cjs:91`、`:123`），压掉 30~44px 的脚底上下位移
  （`import3.cjs:87`）；最终 bg9 162 帧图集回读复测：每组脚底 y 跨度 = 0px，仅 react 组 1px（跳跃真位移，见第 6 节）。

## 1. 每组各自 fit-to-box（规则 13）

- **现象**（不这么做时）：全局单一缩放会让横构图撑爆格子、竖构图小到看不清（见第 3 节）；
  逐帧缩放会忽大忽小（见第 0 节）。fit-to-box 是同时避开这两个坑的唯一解。
- **根因**：组与组的构图比例天然不同，帧与帧的位移是真实动作。归一化的正确粒度是**组**：
  组间允许形状不同，组内必须刚体一致。
- **修法**（定义与公式）：

  ```
  组并集框 u = ∪ 每帧 alpha>8 的内容 bbox          （并集，不是逐帧）
  s  = min(BOX_W / u_w, BOX_H / u_h)               （每组各算一个 s）
  dw = round(u_w × s),  dh = round(u_h × s)        （组内所有帧共用这一个 s）
  裁切：每帧都按【组并集框】裁，绝不是逐帧紧裁
  落点：px = round((CELL_W − dw)/2)   水平居中
        py = BASELINE − dh            底边对齐 baselineY
  ```

  证据：
  - 原型 `qanimal/pack162.py:10-11`（docstring 原文：「每组各自 fit-to-box：s = min(BOX_W/组并集宽,
    BOX_H/组并集高)，组内所有帧共用这一个 s，取【组并集框】裁切（不是逐帧紧裁）⇒ 组内零抖动；
    底边对齐 baselineY，水平居中」）；alpha>8 阈值 `pack162.py:200`；并集 `:204`；s=min `:209`；
    px/py 底边对齐+水平居中 `:211`；按组并集框裁切 `:229`（`sub = im[u[1]:u[3]+1, u[0]:u[2]+1]`）；
    贴图共用组级 dw/dh/px/py `:236`。
  - 正式打包器 `petwork/tools/sprites.mjs:938-941`（precut 路线头注释）、`:942`（`cmdStatesPrecut`）、
    `:945`（THR=8）、`:956-963`（逐帧 bbox → 组并集）、`:967`（`s = Math.min(BOX_W/uw, BOX_H/uh)`）、
    `:969`（底边对齐 BASELINE + 水平居中）、`:970-972`（内容盒越出安全区直接 exit(2)）、
    `:983-998`（pass2：按组并集框裁 → 组统一缩放 → 贴进 sheet，全组共用 g.px/g.py）。
  - 几何常量：cell 112×150、baseline 134、8×21 格（`sprites.mjs:27`），内容盒 BOX 98×118，
    「左右≥7px、上下≥16px 余量，保证任何帧不触 cell 边」（`sprites.mjs:29` 注释原文）；
    meta 实例 `petwork/out/pet.json:4-13`（cell/cols/rows/display）、`:18`（baselineY=134）、
    `:765-768`（cellBox 98×118）。
- **为什么组内放置抖动 = 0**：组内「缩放、裁切框、落点」三个量都只有一份，帧与帧之间唯一能动的
  就是内容本身 ⇒ 帧间位移 = 真实动作，放置抖动恒等于 0。`pack162.py:231-233` 还专门把每帧内容
  换算成贴图后的「真实脚底 y」用于量化组内抖动，`:249` 打印注明「跨度 = 真实动作幅度，不是抖动」。
- **实测数字**（bg9 162 帧、8 组，`pet.json:763` files=162、`:771-884` source.groups 实测值）：

  | 组 | 帧数 | 并集框 w×h | s | 内容 w×h | 脚底 y |
  |---|---|---|---|---|---|
  | walk（`pet.json:772-785`） | 22 | 704×694 | 0.1392 | 98×97 | 134 |
  | react（`pet.json:786-799`） | 14 | 1088×716 | 0.09007 | 98×64 | 134 |
  | idle（`pet.json:800-813`） | 23 | 580×657 | 0.16897 | 98×111 | 134 |

  八组 s 各不相同（0.09007~0.16897，相差 1.87 倍），但组内每帧共用一个 s，脚底全部落在

## 2. 归一化基准必须是常数，不能是 max() over data（规则 15）

- **现象**（真实事故）：素材目录混进一张异规格超大图——「报错装死/7.png」1088×2176、内容高 1971px
  （`qanimal/dead.cjs:1`；`qanimal/import3.cjs:61-62`、`:90` 注释原文记录该尺寸与内容高）。
  它把「对数据取 max()」的归一基准拖垮：全组帧被缩到 **0.4632 倍**（`import3.cjs:90` 注释原文
  「全组被压到 0.46 倍」），最惨时另一个视图的 bbox 塌成 **18×25** 的渣（`import3.cjs:62` 注释原文
  「连累同组正常帧被缩成 18x25 的渣」，组倍率被拉到 0.12 ≈ 246/1971）。
- **根因**：归一基准是「世界尺寸」的锚点。锚点若由被测数据算出（max()/percentile 都一样），
  一张脏数据就重新定义了全世界的大小——其余所有正常帧反而成了「异常小」。基准的正确来源是
  显示端需求（目标内容高），与输入数据无关。
- **修法**（两条同时上）：
  1. **目标高度写死成常量**：`import3.cjs:90-91`「固定 246px：不能取全组 max ——异规格大图
     （报错装死/7.png 是 1088x2176、内容高 1971）会把基准带跑」→ `const TARGET = 246`；
     `dead.cjs:9` `TARGET_H = 246`（注释：与 import3.cjs 的归一标准一致）；
     `sprites.mjs:851` `const WANT_H = 176`（注释：「目标：主体高 ≈176px（旧素材 174）」）。
  2. **先隔离异规格大图**：>400px 的单独走另一条路或跳过——`import3.cjs:63`
     `if (img.w > 400 || img.h > 400) → 跳过（交 dead.cjs）`。dead.cjs 这条单独路线也不是直接塞进组里，
     而是按横向空带切成多帧、丢掉「高 < 主体 35%」的水印条（实测 7.png 底部水印条 212×55，
     只有主体高 589 的 9%）后按参考格对齐单独入格（`dead.cjs:40-53`、`:65-72`）。
- **实测数字**：隔离前组倍率 0.12 / 0.4632、单帧 bbox 塌成 18×25；隔离后倍率 = 246/组内干净数据的
  最高内容（`import3.cjs:92-93` 逐组打印归一倍率），dead 参考格对齐用「量 idle 第 1 帧在图集里的
  实际内容高与脚底 y」而不是信源图尺寸（`dead.cjs:65-72`），保证屏幕上大小一致。

## 3. 横竖构图必须分开归一（规则 16）

- **现象**：同一批素材里横竖构图并存——庆祝完成（react）并集 1088×716、睡觉休息（sleep）并集 1065×639
  是横构图；待机眨眼（idle）580×657 是竖构图。任何「单一方向」的全局归一都会顾此失彼。
  （中文组名→状态映射见 `import3.cjs:8`：`'待机眨眼':'idle'、'庆祝完成':'jump'、'睡觉休息':'sleep'`；
  并集实测值见 `pet.json:788-793`、`:844-849`、`:802-807`。）
- **根因**：
  - 按高度归一 ⇒ 横躺的撑爆格子：react 若取 s=118/716=0.1648，宽变成 1088×0.1648≈179px，
    远超内容盒 98px、甚至超出 cell 宽 112px（触边/越盒会被打包器直接拒绝，`sprites.mjs:970-972`）；
  - 按宽度归一（全组钳一个最大宽）⇒ 竖构图被连累变小：真实踩坑记录在 `sprites.mjs:854-855`
    注释原文——「不能再拿 MAX_CELL_W(168) 钳宽度——那是给竖构图旧素材定的，对 380px 宽的横构图
    会把整体缩放压到 0.44、角色只剩 133px 高（实测踩过）」，另见 `:849-850`（宽身角色塞竖格子
    「实测 s=0.44 → 168x133 头顶空 68px」）。
- **修法**：fit-to-box 的 min() 天然就是「横竖分开归一」——横构图被宽度钳制（s=BOX_W/u_w），
  自然又扁又宽；竖构图 u_w 小、s 大，自然又窄又高。**横躺的角色就该又扁又宽，这是正确的形态，
  不是缺陷**；不需要人工判横竖，每组 min() 自动得到各自的结果。
- **实测数字**：react s=98/1088=0.09007 → 内容 98×64（扁宽）；sleep s=98/1065=0.09202 → 98×59；
  idle s=98/580=0.16897 → 98×111（窄高）（`pet.json:794-798`、`:850-854`、`:808-812`）。
  三组内容高 64/59/111 相差近一倍，但脚底都在 y=134、水平都居中（`pet.json:18`；公式 `sprites.mjs:969`），
  屏幕上读作「同一只角色的不同姿势」，而不是「不同大小」。

## 4. 缩放插值：缩小 ≥2× 用面积平均（规则 17）

- **现象**：大图直接双线性缩小 ≥2 倍时出锯齿，动画帧间闪烁。
- **根因**：双线性每个目标像素只采 2×2 邻域。`sprites.mjs:345` 注释原文：「1280→98 的双线性只采 2×2、
  丢 97% 信息，帧间会闪烁」——13.1× 缩小时 footprint 是 13×13，只用 4 个样本（信息利用率 4/169≈2.4%）；
  相邻帧采样点落在不同源像素上，输出就抖。
- **修法**：缩小倍率 ≥2 自动切面积平均（INTER_AREA 语义），<2 才用双线性：
  - python 侧：`cv2.resize(sub, (dw, dh), interpolation=cv2.INTER_AREA)`（`qanimal/pack162.py:160`）；
  - node 侧：`resizeRGBA`（`sprites.mjs:345-348`）判 `sw/dw >= 2 || sh/dh >= 2` 走 `resizeBoxRGBA`
    面积平均（`:349-372`，dst 像素 = footprint 内全部 src 像素的预乘 alpha 平均，注释自证
    「与 pack162.py 的 INTER_AREA 同语义」），否则走 `resizeBilinearRGBA`（`:373-395`）。
- **实测数字**：切换阈值 = 2×（`sprites.mjs:346`）；本图集最深的 react 组 s=0.09007 ≈ 11.1× 缩小、
  idle 组 0.16897 ≈ 5.9× 缩小（`pet.json:794`、`:808`），全部走面积平均路径；回读复测
  「每帧最少非透明 >1200px」全过（门槛见第 6 节），没有被缩成噪点的帧。

## 5. 尺寸不变量推理：k = display / cell，不变量是屏幕 CSS px

这是整条链路最易错、也最值得单独成节的一条推理。

**显示尺寸的不变量是「屏幕上的 CSS px」，不是「cell 内的 px」。** 引擎把 cell 放大到 display 上屏，
设 k = display / cell：

- **内嵌模式**：cell 112×150（`sprites.mjs:27`；`pet.json:4-7`），display 192×224（`sprites.mjs:34`；
  `pet.json:10-13`）⇒ k = 224/150 = **1.4933**（`pack162.py:13` docstring「displayScale = 224/150」；
  `pack162.py:36` `DS = 224.0/CELL_H`，公式 = display 高 ÷ cell 高）。
  内容盒 98×118（`sprites.mjs:29`；`pet.json:765-768`）⇒ 上屏 98×1.4933≈146、118×1.4933≈176.2，
  即 **146×176 CSS px**（`sprites.mjs:31` 注释原文「98×118 上屏 146×176」）。
- **高清模式**：cell = display = 192×224 ⇒ k = 1。此时内容盒必须按 k 反算成 **146×176**，
  上屏尺寸才与内嵌模式一致（`sprites.mjs:30-32` 注释原文：「BOX 的不变量是『内容在屏幕上的 CSS px』，
  不是『cell 内的 px』……换 cell 尺寸时 BOX 必须按 k 反算……否则桌宠会在两种素材间悄悄变大/变小」）。
- **直觉错法**：按 cell 等比取 168×200——高 200 对上屏容量 176 是 200/176 ≈ **+13.6%**，
  桌宠悄悄变大 13.6%，而两种模式的**元素 style 尺寸都仍是 240×280**（见下），
  所以只比元素尺寸抓不出这个 bug，必须比「内容的屏幕 CSS px」。
- **为什么元素尺寸抓不出来**：元素尺寸 = display × scale × PAD(1.25)（`sprites.mjs:33` 注释原文），
  display 两种模式都是 192×224 ⇒ 元素实测基线 **240×280**（`sprites.mjs:1056` 注释原文
  「元素 240×280、内容高≈176 CSS px」）。元素尺寸完全由 display 决定，与内容盒无关——内容盒错了它照样对。
- **内容高容量核对**：118 × 224/150 = **176.2px ≈ 旧版 176**（旧基线 WANT_H=176，`sprites.mjs:851`；
  `pack162.py:278` 打印同款核对「BOX_H × ds vs 旧版 WANT_H 176」）。pack162 时代内容盒高 116 时
  是 116×1.4933≈173，与旧版 176 差 3px（`pack162.py:15` docstring 实测记录）；正式打包器取 118 恰好补齐。
- **历史教训**（display 字段为什么存在）：引擎 geometry() 里 dw = cw×scale，显示尺寸直接由 cell 决定，
  cell 从 192×224 缩到 112×150（宽比 112/192=0.583）会让桌宠跟着缩小 42%（`pack162.py:13-14` docstring
  原文「格子缩小 0.583 倍会让桌宠跟着缩小 42%」）。修法是把 displayScale 写进 meta、渲染时补乘
  （`pack162.py:109-118` 补丁、`:254` 写入 meta）；正式打包器把它规范化成 `meta.display` 字段
  （`sprites.mjs:1056`；`pet.json:10-13`）。
- **结论**：验收必须**同时断言**元素尺寸（240×280）和内容 CSS px（内容高 ≈176、内容盒按 k 反算）。
  `tools/smoke.mjs` 已按此设计并交付（kit 引擎 + demo meta 实测 142 PASS / 0 FAIL；负测试塞 [99,99] 越界坐标
  → FAIL 精确命中、exit 1；链路位置见 `README.md:38`、`:78-81`）。

## 6. 验收指标与 alpha 阈值伪影（规则 18）

- **现象**：验收数字会「差 1~2px」，容易被误判成放置抖动，也容易被用来放水。
- **根因**：素材边缘是 1px 羽化的 alpha 渐变（`cutall.py:19`、`:150-151` 高斯模糊 alpha 斜坡），
  半透明圈上的像素「算不算内容」完全取决于阈值：alpha>8 与 alpha>128 量出来的 bbox/跨度可能差 1~2px。
  **那是阈值伪影，不是抖动。** 所以复测代码的口径必须与打包器一致：「alpha>8 算内容；脚底=y1+1；
  质心x=sum(x)/count（cell 内局部坐标）；触边=内容碰到 cell 四边；空格必须全透明」
  （`petwork/tools/verify-hd.py:2-3` 注释原文）；打包器同口径（`sprites.mjs:941`「alpha>8 阈值、
  与素材侧测量口径一致」、`:945` THR=8；`pack162.py:200` 同为 >8；`sprites.mjs:829` 另有一条
  用 128 的路径——跨工具比数字先对阈值）。
- **修法**（指标表，判据代码全部核实）：

  | 指标 | 门槛 | 判据证据 |
  |---|---|---|
  | 每组脚底 y 跨度 | = 0px（react 允许 1px，那是跳跃真位移；gate 代码上限放到 3px） | `sprites.mjs:1033`、`verify-hd.py:64`（`fy <= 3`） |
  | 质心 x 跨度 | 小即可（横向动作如 walk 除外；只报告不判死） | `sprites.mjs:1032-1035`、`:930-933` |
  | 内容触边 | = 0（任何帧内容不得碰 cell 四边） | `sprites.mjs:741`、`:1025`、`verify-hd.py:58-59` |
  | 空格残留 | = 0（未占用 cell 必须全透明） | `sprites.mjs:748-756`、`verify-hd.py:70-82` |
  | 最小占用 | 每帧非透明 > 1200px（有下限，防缩成噪点/空帧） | `sprites.mjs:745`、`:1033`、`verify-hd.py:64` |

- **实测数字**：bg9 162 帧图集按上表回读复测全过——每组脚底 y 跨度 0px（react 1px，跳跃真位移）、
  触边 = 0、空格残留 = 0（168 格用 162、空格 6 个全透明）、每帧最少非透明 >1200px；
  成品 PNG 2,548,445B ≈ 2.43MB，在 3.2MB 硬上限内（`pet.json:770` pngBytes；上限判定打印

## 7. 打包完必须回读成品独立复测（规则 19）

- **现象/风险**：打包器的自述（「我按 s=0.16897 贴在了 (7,23)」）只能证明「我做了我想做的」，
  不能证明「落盘的 PNG 真的是这样」——编码器 bug、贴图越界、行距算错、写错文件都会悄悄毁掉成品，
  而自述数字依然漂亮。
- **根因**：自述与成品走同一段代码，共享同一套错误假设。要抓住「写出来的不是我以为的东西」，
  必须从成品出发、用另一套代码再量一遍。
- **修法**（三层）：
  1. **打包器回读自测**：写完 spritesheet.png 立刻解码回读，逐组实测脚底跨度/质心跨度/触边/占用
     （`sprites.mjs:1010-1035`，`:1010` 注释原文「回读成品实测」）；
  2. **另一套代码独立复测**：`petwork/tools/verify-hd.py` 用 python/cv2 复测同一成品——`:1` 注释原文
     「用 python/cv2 **独立**复测高清图集（与 sprites.mjs 的回读复测是两套代码）」；复核尺寸与 meta
     一致（`:28-30`）、cell 重复占用（`:45-46`）、每组跨度/触边/占用（`:38-68`）、空格残留（`:70-82`），
     最终打印不合格数并据此定退出码（`:85-86`）；另有纯结构校验 `cmdVerify`（`sprites.mjs:717-758`）；
  3. **素材侧同样先独立测量再动手**：`petwork/measure/report.md` 是 measure.mjs 产出的纯测量报告
     （「纯测量，未改动任何素材文件」「可重跑」，`report.md:1`、`:3`）。它的价值被实证过：正是这套
     独立测量发现「若按『最下非背景行』取脚底会得到 y=2007——那是独立地面阴影条的底，
     对齐基线请用主域底边 y=1788/1850/1808」（`report.md:65` 原文）。若打包侧直接用整图前景 bbox
     裁帧，角色会整体下沉 157~219px（2007−1850 / 2007−1788）。
- **实测数字**：report.md 记录三张 2048×2048 素材前景占比 23.3%/24.3%/23.5%（`report.md:14`、`:28`、`:42`），
  主域底边 1788/1850/1808 vs 阴影条底 2007；~1.4k px 的阴影条被「域面积 ≥8000px」过滤线天然剔除
  （`report.md:3`、`:66`）。verify-hd.py 的判据（`fy<=3`、`min(cnts)>1200`、`touch==0`、空格全透明）
  与打包器 gate 逐项同口径（`verify-hd.py:64`、`:78` vs `sprites.mjs:1033`、`:753`）。
