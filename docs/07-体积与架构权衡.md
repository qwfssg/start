## 规则 37 · /plugins 只服务预组合 bundle ⇒ 外挂大图集必须自注册 HTTP 路由

三个事实，全部实读核实：

1. **/plugins 路由本身就是一条注册出来的 prefix 路由**：`@deepseek-ai/dsh-client-modules/lib/index.js:480-484`——`ctx.effect(() => ctx.webServer.register({ kind: "prefix", path: "/plugins", handler: this.serveBundle }), "client-modules: bundle route")`。
2. **serveBundle 只查内存 map，不读文件系统**：:838-858——解析请求 URL（:845-846）后查 `this.responses.get(resourceUrl) ?? this.previousBatchResponses.get(resourceUrl)`（:847），命中回 200 + `IMMUTABLE_CACHE`（:848-854），**未命中回裸 404**（:856-857，`res.writeHead(404); res.end()`，无正文）。map 只由预组合产物填充（:585-594 `responses.set(artifact.url, …)`）。⇒ **插件的 assets/*.png 用任何 URL 组合都是 404，且无 HTML 回退**——`/plugins/**` 已被具名前缀路由接住，永远到不了 webserver 的 fallback 席位（`@deepseek-ai/dsh-host-webserver/lib/index.js:232-243`：match 命中即进 handler，只有没有任何具名路由匹配时才轮到 fallback）。实测记录：**8 种候选 URL 全 404**（`dsh-pet-bg/lib/index.js:41-43` 注释原文「插件 assets 用任何 URL 组合都是 404（8 种候选实测全 404）」；逐条清单未留档，见文末待核实 1）。
3. **但任何宿主插件都能自己注册 HTTP 路由**：`dsh-host-webserver/lib/index.js:176-183` `register(route)` 收 `{kind:"exact"|"prefix", path, handler}`，重复 (kind,path) 抛错（组合级契约）；:321-331 `match()`——exact 表优先（:323-324），prefix 表**最长前缀优先**（:321 注释原文「Longest-prefix-wins over the prefix table after an exact-table miss」，选择环 :326-328）。**核心不对具名路由做鉴权**：register（:176-183）与请求分发（:228-244）全程没有任何鉴权检查，任何同源请求直接打到 handler（`dsh-pet-bg/lib/index.js:35-37` ★安全须知★同结论）⇒ 文件名白名单是唯一防线（:38-40：只认两个文件名、`path.basename` 后**严格全等**、绝不做通配静态服务器、刻意不 `decodeURIComponent` :88；12 条穿越/越权用例全 404，pet-smoke:607-624 断言 106）。

先例（均实读核实，行号无漂移）：
- 官方：`@deepseek-ai/dsh-webhook-github/lib/index.js:190`——`ctx.effect(() => ctx.webServer.register(route), \`webhook-github: ${config.path}\`)`，route 为 `kind:"exact"`（:181-189）；`inject` 声明依赖 `webServer`（:162-166）。
- 第三方在线：`dsh-workbench/lib/index.js:27`——`export const inject = ["connection", "webServer"]`；:184——`ctx.webServer.register({ kind: "exact", path: STREAM_PATH, handler: stream.handler })`。

⇒ **外挂大图集完全可行，落地代码约 6 行**。本仓库 `plugin/lib/index.js` 就是完整实现：

```js

ctx.effect(function () { return ctx.webServer.register({       // :118-121
  kind: "prefix", path: "/pet-assets", handler: petAssetHandler }); }, "pet-assets");
function petAssetHandler(req, res) { /* basename 白名单 :67-78 → stat :82 */
  createReadStream(file).pipe(res); }                          // :95-103
```

客户端同源拉取：`fetch(url, { credentials: 'same-origin' })`（`dsh-pet-bg/src/pet.js:288-289`），base 缺省 `/pet-assets`（:352），先取 `pet-hd.json` 再取 `spritesheet-hd.png`（:355-364），每步 8s 超时、fetchSoft 永不 reject（:255、:273），任何失败静默回退内嵌（:249-251 注释列全失败面：404/网络错/超时/JSON 坏/摘要不符/解码尺寸不符）。

**代价**：宿主侧代码在服务启动时读一次（docs/06 规则 36）⇒ 新增/改动路由**必须重启服务一次**（README.md:102 原文「宿主侧 `lib/index.js` 只在启动时读一次（改它必须重启服务）」；deploy-hd.ps1:9、:61）。因此设计上要求「重启前也必须能跑」：客户端取不到外挂就静默回退内嵌版（`dsh-pet-bg/lib/index.js:14-16` 注释原文「『路由还没生效（宿主未重启）』这段时间桌宠照常工作」；pet-smoke:736-740 断言 113 把「404=重启前」写成必过用例）。

## 规则 38 · 自制路由要自己负责：缓存失效、内存、gzip、体积上限

- **官方 bundle 免费拿到「内容哈希 rev + immutable」**：`IMMUTABLE_CACHE = "public, max-age=31536000, immutable"`（dsh-client-modules:121-122，注释原文「Versioned code is immutable; mismatched revisions are rejected instead of serving newer bytes」）；rev = sha1 内容哈希前 12 hex（:167-169）；URL 自带 rev（:182-183 `/plugins/??<id>/client.js&rev=<rev>`；:328-333 注释原文「url carries the rev as its cache-busting query」）；serveBundle 命中即回 immutable（:849-852）。**自制路由这些全没有，要自己补。**
- **补法一：?v=<hash>**（已落地实例）：路由发一年 immutable，客户端用 `?v=<图集内容 sha256 前 16 位>` 请求——内容一变 URL 就变，缓存天然失效（`dsh-pet-bg/lib/index.js:47-49`，警告注释原文「千万别在这里改成不带 ?v= 也能缓存的写法，否则换素材后浏览器会永远用旧图」）。构建侧闭环：`copy-hd.mjs:10-13` 注释原文解释为什么必须带哈希（immutable + ?v= 失效 + 「pet-hd.json 里的 sheetHash == 实际下载到的 PNG 的 SHA-256 == 构建期写进 client.js 的常量」三方校验，任一不符静默回退 ⇒ 版本错配永不上线），:38-41 注入 `sheetHash/sheetBytes/hd`；`embed-sheet.mjs:73-108` 把它算成 `src/sheet.js` 里的 **SHEET_HD 常量**（:85-89 构建期 sheetHash 与实算不符直接 die；:95-96 `jsonRev/pngRev`；:97 `pngSha256`；缺高清素材时 `SHEET_HD = null`，:77、:107）。**漂移说明**：母文本引 :64-105，实读 :64-71 是生成文件的 banner 注释，SHEET_HD 构造块实在 :73-108。客户端执行侧：`crypto.subtle.digest('SHA-256')` 校验下载字节（pet.js:317-323，:321 摘要不符 throw → 静默回退；:318 非安全上下文没有 subtle 时跳过摘要、仍有字节数+形状+解码尺寸三重校验）；「?v= 用内容哈希而不是时间戳」有专门断言（pet-smoke:783-784 断言 131）。
- **补法二：ETag**（线上 dsh-pet-bg 版）：弱 ETag 只用 size+mtime、不为校验和重读 9MB（`dsh-pet-bg/lib/index.js:101-104` 注释原文）；`If-None-Match` 命中回 **304 一个字节都不传**（:69-80 etagMatches 弱比较、:106-114），给「硬刷新/缓存被清」兜底（:102-103）；冒烟连 304 响应体为空都断言（pet-smoke:599-606 断言 105b/105c）。本仓库提纯版 `plugin/lib/index.js:86-91` 只保留 ?v=+immutable、去掉了 ETag/304——提纯取舍：?v= 已足够失效，304 只在「缓存被清后回源」省一次流量。
- **用 createReadStream，别把大文件读进内存**：`dsh-pet-bg/lib/index.js:96-97` 注释原文「流式发送：高清图集 ~9MB，绝不整块读进内存」（实测高清图集 9,369,302 B；母文本的「5MB」是量级说法，按文件与实物为 ~9MB）；:127-135 流 error → `res.destroy()`；本仓库 `plugin/lib/index.js:80-81`（同注释）、:95-103 同构。冒烟的假 res 也只数字节不留内容（pet-smoke:569-573 注释原文「只数字节，不留 9MB 在内存里」）。
- **gzip 中间件会跳过 PNG**：webserver 的压缩层把 filter 委托给 npm `compression` 的默认过滤器（dsh-host-webserver:106-116，:110-115；gzip 对所有请求生效 :257-258），该过滤器按 content-type 是否可压缩决定（compression/index.js:280-281「not compressible → 跳过」），`mime-db` 对 `image/png` 标注 `compressible:false`（node_modules/mime-db/db.json 实读；dsh-host-webserver/README.zh.md:41「媒体类型必须可压缩」）⇒ 即便宿主开了 gzip，PNG 也不会被白压一遍。
- **自制路由没有体积上限**：register 与分发路径（dsh-host-webserver:176-183、:228-244）没有任何尺寸检查；4.0MB 硬限只是**内嵌路线的构建期**约束（embed-sheet.mjs:22）。体积闸门只能应用层自设——对照 dsh-bg 给存储视频自设 300MB 软上限（dsh-bg/lib/client.js:327-328 注释原文「IndexedDB can hold far more; this guards abuse」）。

## 规则 39 · 不想重启服务的另一条路：内联 data-URL 与 IndexedDB 导入（dsh-bg 先例）

第三方 dsh-bg（`D:\dsh\node_modules\dsh-bg`）**不用 HTTP 传二进制**，两条腿都在浏览器侧：

- **示例背景 = 内联 data-URL SVG**：`dsh-bg/lib/client.js:24-25`——`SAMPLE_SVG` 是 1600×900 渐变 SVG 的源码常量（:24），`SAMPLE_DATA_URL = "data:image/svg+xml;charset=utf-8," + encodeURIComponent(SAMPLE_SVG)`（:25）。与本项目内嵌精灵图集（`data:image/png;base64,`，embed-sheet.mjs:54）同一手法：素材进 JS，零请求、零路由。
- **用户视频 = IndexedDB → URL.createObjectURL**：库名/仓名 `dsh-bg`/`media`（:329-331）、单视频 300MB 软上限（:327-328）、`openMediaDb` 首用建仓（:338-347）、MP4 条目 blob 存 IndexedDB（:411）、播放时 `idbGet → URL.createObjectURL` 且 object URL 只在内存缓存（:482-502，:493-496；缓存 map :332-333）；`dsh-bg/README.md:49` 原文「动态壁纸（MP4）：上传 MP4 视频作为背景，静音循环播放；视频 Blob 存 IndexedDB」。

`dsh-pet-bg/src/bg.js` 的背景视频层就是同款 IndexedDB 方案（实读引用）：
- 面板提示原文「参数存 localStorage，视频存 IndexedDB（二进制绝不进 localStorage）」（bg.js:105）；
- 源二分：clip（IndexedDB）/ url（http/https 白名单）（bg.js:134）；
- 上传 → `CORE.putMedia(rec)`，注释原文「Blob 只进 IndexedDB，绝不进 localStorage」，配额失败有明确提示（bg.js:218-222）；
- 存取实现：`putMedia`（core.js:229）、`getMedia`（core.js:237）、取回后 `URL.createObjectURL(record.blob)`（core.js:261-263）；
- 设计文档：IndexedDB `dsh-pet-bg` → store `media`（keyPath id）（DESIGN.md:62）；「objectURL 只在内存里缓存，revoke 于替换/删除时；**刷新后重新 createObjectURL**（URL 不进 localStorage）」（DESIGN.md:66）。

**适用场景**：这是「不想（或不能）重启服务」时的另一条路——宿主侧零代码，一切在浏览器完成；代价是**用户首次使用时要手动导入一次素材包**（上传/选文件），且素材跟浏览器 profile 走、不随安装包分发、换浏览器要重导。精灵图集主路径没有选它，因为图集要求「装好即有」：内嵌 data URL 保证部署完成素材就在包里，IndexedDB 适合视频、自定义皮肤这类**可选的重素材**。

| 维度 | A · 内嵌 data URL（现行内嵌路线） | B · 外挂 HTTP 路由（/pet-assets） | C · IndexedDB 导入 |
|---|---|---|---|
| 重启服务 | **免**（刷新即生效，docs/06 规则 36；install.ps1:8-10） | **需一次**（宿主代码启动时读一次，README.md:102）；重启前静默回退 A（pet-smoke 断言 113，:736-740） | **免**（宿主零代码） |

| 素材能力上限 | 162 格 @112×150（PNG 2.43MB→base64 3.24MB 是放行极限；**319 格的 8.94MB→11.9MB 塞不进**，embed-sheet.mjs:74-75 注释原文） | **可回全清晰度与全帧数**：319 格 @192×224、PNG 8.94MB（1536×8960）已实际上线（README.md:147-152） | 任意大小，但见右列用户动作 |

**隐性成本（A/B 共有，必须写进决策）——引擎离屏预切内存**：引擎把每个 cell 离屏预切成独立小 canvas（pet.js:202-206 `buildCells` 与注释：预切是为避免「每帧对大图集算源矩形时非整数源坐标在不同浏览器取整不一致造成的 1px 缩放抖动」），**内存 = 格数 × cell 面积 × 4B**（pet.js:1064 `cellMemMB` 公式 `cellCount × cell.w × cell.h × 4 / 1048576`；:268-269 启动时把离屏内存打进 console）：

- 内嵌 168 格 @112×150 ≈ **11MB**；
- 外挂高清 320 格 @192×224 ≈ **55MB**（**涨 5 倍**）；另加图集本身解码 1536×8960×4B ≈ 52.6MB、首次加载多下 8.94MB（之后 immutable 缓存命中）（dsh-pet-bg/README.md:176-177；该处按 MiB 记作 10.8/52.5，与 11/55 是同一字节数的两种进制口径；冒烟实跑打印两模式数值并断言 168+320+1 个画布数，pet-smoke:772-774 断言 125）。

**这不是致命问题**（桌面场景几十 MB 量级），**但它是「帧数越多越好」的真实代价**；省内存的方向是「按状态惰性预切 + LRU」（README.md:179，不在当前范围）。

**实测体积系列**（母代理实测，不得换成估算；字节级复核锚点见 docs/06 规则 30 表）：

| 素材 | PNG | base64 | client.js |
|---|---|---|---|
| 40 格 @192×224 | 1.64MB | — | 2.36MB |
| 162 格 @100×136 | 2.21MB | 2.95MB（可过 3.2 硬限的降格子方案） | 3.20MB |
| 162 格 @112×150 | 2.43MB | 3.24MB（**原 3.2MB 硬限会拒，已提到 4.0MB**） | 3.51MB |

**必须写明的结论（实测教训）**：319 格 @192×224 实测 PNG **8.94MB**，比「按 Mpx 线性外推」的 **6.9MB 大 30%** ⇒ **线性估 PNG 体积会系统性偏低，帧数多/内容复杂时更明显**（dsh-pet-bg/README.md:180-181 注释原文：「319 格 @192×224 实测 8.94 MB，比按 Mpx 线性外推的 6.9 MB 大 30% ⇒ 『按像素数线性估 PNG 体积』会系统性偏低（帧数多、内容复杂时更明显）」；embed-sheet.mjs:74-75 同数据）。做体积预算时不要用 Mpx 线性外推，按同源同工艺的实测值校准并留 ≥30% 余量。

**选路速查**：
- ≤162 格且 base64 ≤4.0MB → **A**（零用户动作，现行缺省）；
- 要全清晰度全帧数（319 格起）→ **B**（一次重启；与 A 可叠加：B 失败静默回退 A，线上现行形态就是 A+B——内嵌 162 格保底 + /pet-assets 外挂 319 格高清，右键菜单末项实时显示当前素材来源，README.md:182-184；冒烟断言 115/128，pet-smoke:742-743、:779-780）；
- 不想动宿主、用户接受一次导入 → **C**（适合视频/自定义皮肤等可选重素材，规则 39）。
