## 这一步在流水线里的位置

```
视频 .mp4/.avi ──01 extract_frames.py──▶ frames/f%04d.png + index.txt + scenes.txt + contact/
                                          │
                                          ▼
                        02 key_green.py（逐张抠图，重测每帧背景色，与 index.txt 交叉核对）
```

抽帧是整条链的第一道工序，它决定后面所有工序的**上限**：帧数上限（源视频有多少帧）、时长上限（源 fps 说了算）、分组依据（场景段 + contact sheet）。它的产物契约：

| 输出 | 内容 | 给谁用 |
|---|---|---|
| `f%04d.png` | 原始帧（f0001 起 1 基编号，不抠图不裁剪不改尺寸） | key_green.py 的输入 |
| `index.txt` | 每帧一行：`帧号 时间(s) 边框背景色 rgb(...)`；文件头注明源视频 fps/时长/总帧数/抽帧间隔 | 对账、交叉核对、事后回溯 |
| `scenes.txt` | 按边框背景色自动分段：`段NN fXXXX ~ fYYYY (n 帧, a~bs) 背景 rgb(...)` | 动作分组的机器初稿 |
| `contact/contact-NN_fXXXX-fYYYY.png` | 缩略图矩阵，帧号烧在图上，每 `--contact-every`（默认 80）帧一张 | 人审分组（01 阶段唯一的人审检查点） |

### 用法

```powershell
# 常规：每 2 帧抽 1
python tools\extract_frames.py --input 视频.mp4 --out frames --every 2

# 只测量不落盘：打印 fps/时长/总帧数/计划抽取数/分段计划
python tools\extract_frames.py --input 视频.mp4 --out frames --dry

# 带循环段检测（每个场景段内找循环候选并给判定）
python tools\extract_frames.py --input 视频.mp4 --out frames --every 1 --detect-loops

# 秒区间 + 帧数上限（超了均匀稀释，提纯自 video2sprite.py:128-132）
python tools\extract_frames.py --input 视频.mp4 --out frames --every 1 --start 0.5 --end 1.5 --max-frames 120
```

CLI 全表：`--input`（必填，视频路径）/ `--out`（非 --dry 必填）/ `--every N`（每 N 帧抽 1，默认 1；0=按 --max-frames 自动算间隔，同 video2sprite.py:113-114）/ `--max-frames N`（0=不限）/ `--start`、`--end`（秒，含端点，可选）/ `--contact-every N`（默认 80）/ `--detect-loops` / `--dry`。退出码：0 成功；2 视频不存在/打不开/参数非法；3 一帧都没抽到；4 有文件写失败。中文/空格路径先转 8.3 短路径再喂 VideoCapture（video2sprite.py:76-85）；帧 PNG 落盘一律走 `kg.imwrite_u`（imencode+tofile，中文路径下 cv2.imwrite 会静默失败，见 docs/08 第 15 条）。

## 为什么要记录 fps / 时长 / 每帧边框背景色：index.txt 的三个作用

**作用一：fps 和总帧数是"承诺上限"的凭证。** 动画时长 = 帧数 ÷ 播放 fps，而帧数上限被源视频锁死。index.txt 文件头把源 fps/时长/总帧数/抽帧间隔写死在产物里，后面任何人想承诺播放帧率，先看这一行（真实教训见下文"源 24fps 就别承诺 60fps"）。它还是对账工具：容器声称的总帧数可能虚报，本工具抽完会比对"源声称 vs 实际读出"，不一致打 `[!]`（以实际读出为准）。

**作用二：每帧边框背景色是场景分段的原料。** 取色方法与抠图完全同源：四边 6px 边框带内像素的众数色，RGB 各通道量化到 8 的倍数再投票（`tools/key_green.py:110-124` `border_modal`，width=6、quant=8）。量化压掉压缩噪点，边框带保证取到的是纯背景而不是角色（原版同款思路：video2sprite.py:88-98 `modal_color` + 327-332 的 6px 边框掩码，"比取四角稳，四角可能是阴影或留白"）。注意原版量化到 4、本仓库统一量化到 8（差异见文末待核实第 4 条）。

**作用三：它是与 key_green.py 的交叉核对基线。** 抠图阶段**不信任** index.txt，每张图独立重测一遍 `border_modal`（`tools/key_green.py:415`），两次测量写进各自的产物（index.txt vs keyed/report.txt）。同一帧两个数字对不上，说明中间有人动过图或取色带宽/量化档不一致——问题在入库前暴露，而不是在成品桌宠上"背景抠不净"时才发现。本次交付的合成视频实测：extract_frames 记 `f0001 rgb(112,176,80)`，key_green --dry 重测同帧 `bg=rgb(112,176, 80) 覆盖=97.9%`，逐位一致。

## 为什么按背景色分场景：scenes.txt

AI 生成的角色视频常常是"多个动作段拼在一起"的合集，段与段之间最稳定的机器可测信号就是**背景色整体漂移**——同一批素材实测出现过 rgb(120,184,88)、rgb(160,200,88)、rgb(120,184,80)、rgb(175,235,105) 多种绿（docs/02 开头；qanimal/cutall.py:11-13）。scenes.txt 的判据：相邻帧边框背景色**任一通道差 > 24 即切段**；段背景色取段内众数。

真实例子（旧工程留档 `vframes/`，361 帧全量）：

```
# vframes/scenes.txt:2-4（本仓库 examples/frames/scenes.txt:3-5 有同款副本）
段01  f0001 ~ f0096  (96 帧, 0.00~3.96s)  背景 rgb(120,184,88)
段02  f0097 ~ f0275  (179 帧, 4.00~11.42s)  背景 rgb(160,200,88)
段03  f0276 ~ f0361  (86 帧, 11.46~15.00s)  背景 rgb(120,184,80)
```

对应 `vframes/index.txt`（362 行 = 1 行表头 + 361 行帧记录；本仓库 `examples/frames/index.txt:3-14` 收录了 12 帧节选，正好横跨三段三种绿）。阈值 24 的两面在这份真实数据上都能验证：段01→段02 的 R 通道差 |160−120|=40 > 24，正确切开；段03 内部背景在 rgb(120,184,80) 与 rgb(120,184,88) 之间抖动（`examples/frames/index.txt:10-14`：f0276=80、f0300=88、f0319=80、f0340=88），B 通道差只有 8 ≤ 24，不会被误切成碎段——量化到 8 的取色 + 24 的阈值，正好把"压缩抖动"和"真换场景"分开。

scenes.txt 的定位是**分组的机器初稿**：它只回答"哪几帧背景相同"，不回答"这几帧是什么动作"。动作分组（待机/敲代码/庆祝…）由人看 contact sheet 确认（下一节），确认后按组走 key_green.py 的处方（docs/02、`examples/presets.json`）。

## contact sheet：人审分组的依据

每 `--contact-every`（默认 80）张抽取帧拼一张缩略图矩阵，**帧号烧在图上**（左上角红字 fXXXX），文件名 `contact-NN_fXXXX-fYYYY.png` 自带覆盖范围。真实实例：本仓库 `examples/frames/contact-01_f0001-f0080.png`（80 帧一张）；旧工程全量 5 张在 `vframes/contact/`：contact-01_f0001-f0080 … contact-05_f0321-f0361（361 帧 ÷ 80 = 5 张，最后一张 41 帧）。

为什么必须有它：本仓库贯穿性设计原则是"制作者可能看不见图 ⇒ 每一步输出可核对的数字"（README.md:6-8），但**分组**这件事数字替代不了——"f0097 开始角色从待机换成敲代码"只有人看图才能确认。contact sheet 把人审成本从"逐张打开 361 个文件"降到"看 5 张矩阵图"，且帧号烧在图上，人可以直接口述"f0097 到 f0275 是敲代码"，写进 presets.json 的就是这串编号。布局与烧号实现仿 `tools/key_green.py:254-271`（`contact`），区别是烧全局帧号而不是组内序号。

## 真实教训：源 24fps 就别承诺 60fps

实战素材是一段 15 秒的 AI 生成视频，用户要求成品动画 60fps。实测数据（`vframes/index.txt`）：

- 源帧间隔：f0001=0.000s、f0002=0.042s（index.txt:2-3）⇒ 帧间隔 1/24 s ⇒ **源就是 24fps**；
- 源总帧数：361 帧、末帧 f0361=15.000s（index.txt:362）⇒ 15s × 24fps ≈ 361，**这就是帧数上限**。

算术不留情面：60fps × 15s = 900 帧，而抽帧间隔密到极限（`--every 1`，每帧都取）也只能得到 361 帧——**抽帧间隔再密也造不出不存在的帧**，24fps 的源里没有那 539 帧的信息。此时只有三条出路，且必须向需求方明说：

1. 361 帧按 60fps 播：动作时长被压到 6.0s，等于 2.5 倍速快放（桌宠会"抽风"）；
2. 插帧补到 900 帧：光流/AI 插帧在小尺寸角色动画上伪影明显（肢体撕裂、边缘果冻），且引入新的一类质量问题；
3. 换更高 fps 的源，或接受 24fps 上限定播放 fps（本项目最终按素材实际能力配 fps，桌宠播放 fps 本来就是 meta 里的独立参数，不跟源 fps 绑定）。

工程结论：**fps 承诺的凭据是 index.txt 文件头，不是需求方的愿望**。这也是 index.txt 必须把源 fps/时长/总帧数写进文件头的直接原因——争论发生时拿产物对账，不靠记忆。

## 循环段检测原理（--detect-loops）

提纯自 video2sprite.py:253-274（`find_loop`）。桌宠动画要无缝循环，问题是"这段动作的哪一截首尾相接"。判据分两步：

1. **候选 = 首尾帧差最小的子段。** 对场景段内所有帧对 (i, j)（j − i ≥ 3，最小长度同原版 --min-loop 默认 3，video2sprite.py:477）算帧差 D[i][j]（平均绝对差 0~255），取 D 最小的 (bi, bj)：D[bi][bj] 最小说明第 bi 帧与第 bj 帧姿态最接近，bi..bj 播完跳回 bi 时画面跳变最小（video2sprite.py:254-255、259-268）。
2. **判定 = 首尾差与段内最大相邻差比较。** span = D[bi][bj]，inner = max(D[k][k+1])（bi≤k<bj，video2sprite.py:269-270）。若 span ≤ inner——首尾两帧比段内随便一对相邻帧还像——判"循环（正向循环可信）"；否则首尾并不比正常帧间跳变更像，硬接回起点会"咯噔"一下，判"非循环（建议 pingpong 来回播）"（原版同语义：video2sprite.py:271-273 的 verdict 与 :419 的 `pingpong = span >= max(12.0, inner)`）。

与原版的两处提纯差异，都是为了适配"抽帧阶段还没有抠图"：

- 原版 `frame_diff`（video2sprite.py:211-217）在**抠图后的 alpha 掩码**上比（只算有内容的像素）；本工具在 160px 宽的原始小图上比整幅像素。段内背景静止，差异主要来自动作，近似成立；要精确判循环，抠图后拿 report.txt 的数字再核一遍。
- 原版对全片找一个循环段；本工具**在每个场景段内**各找一个候选——跨场景的"首尾像"没有意义（背景都换了）。

每段打印：`段NN fXXXX~fYYYY（n 帧）→ 循环候选 fAAAA~fBBBB（m 帧） 首尾差=… 段内相邻最大差=… 判定：…`。合成视频实测（本文交付时的自测，见下节）：直线运动段判"非循环"（首尾差 0.90 > 相邻最大差 0.32），正弦摆动段（首尾同相位）判"循环"（首尾差 0.03 ≤ 相邻最大差 1.62）——两种判定路径都被真实数据走过。

## 抽帧后交给 key_green.py：衔接方式

```powershell
# 平铺布局直接喂（整目录算一组）：
python tools\key_green.py --src frames --out keyed --group-name demo
# 或按 scenes.txt/contact sheet 人工分组后，每组一个子目录，配 presets.json 按组处方（docs/02）
```

衔接的三个要点：

1. **背景色会被逐张重测，index.txt 只用于交叉核对。** key_green.py 对每张图独立跑 `border_modal`（`tools/key_green.py:415`），从不读 index.txt——这是故意的双重测量：两份产物（frames/index.txt 与 keyed/report.txt）里同一帧的背景色必须一致，不一致即报警（见上文"作用三"的实测）。
2. **帧号约定全链一致。** f%04d 从抽帧一直带到抠图、对比、打包（pack_sheet.py 的 meta 里还是这串号），人审口述、presets.json 处方、report.txt 指标都按帧号索引，不需要任何映射表。
3. **scenes.txt 的段是"处方分组"的起点。** 同一场景段内背景色一致 ⇒ 抠图参数通常一致；段内动作再细分（一段里混着待机+走路）时，靠 contact sheet 人审拆组，再按组配 keep-near/shadow/kill-static（`examples/presets.json` 的 why 字段就是这么来的）。
