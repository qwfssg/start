## 规则 22：显示尺寸必须由 display 声明，不能由 cell 推导

- **现象**：图集为了省 base64 体积把 cell 从 192×224 缩到 112×150（PNG 8.94MB→2.43MB，
  `dsh-pet-bg/README.md:149,158`），桌宠在屏幕上跟着缩小 **42%**（宽比 112/192=0.583；
  历史记录原文「0.583× ⇒ 小 42%」见 docs/03 §5 引 pack162.py docstring）。
- **根因**：早期几何直接由 cell 宽高推导显示尺寸（`dw = cw × scale` 一族公式），元素大小与
  **存储参数** cell 绑死。cell 是存储参数、display 才是显示参数，二者必须解耦。
- **修法**：meta 增加 `display{w,h}`（解析在 `cellMeta()`，`plugin/src/pet.js:155-168`：
  `dspW/dspH = display`，旧 meta 无 display 时回落 `cell × displayScale`、displayScale 缺省 1，
  行为与旧版完全一致——:157 注释原文）。几何改为（`geometry()`，:374-385）：
  - **元素尺寸 = display × scale × PAD(1.25)**：`W = dspW×scale×PAD`、`H = dh×PAD`（:381；
    PAD :17，留白给跳跃/粒子，「25% 留白全放头顶」:382）；
  - **绘制按 cell 纵横比 uniform 放大，无形变**：`dh = dspH×scale`（:379）、
    `dw = dh × (cw/ch)`（:380，注释原文「uniform 放大，绝不拉变形」）；
  - layout 把 W/H 写成 canvas 的 CSS 尺寸（:394-398），物理像素另乘 dpr（:395-396）。
- **实测数字**：display 192×224、scale=1 ⇒ 元素**精确 240×280**，与旧基线（cell=display=192×224
  时代）240×280 **0px 差**——冒烟断言 69/81 硬断言 `style.width==='240px' && style.height==='280px'`
  （`dsh-pet-bg/tmp/pet-smoke.mjs:415, :457`，本机复跑 PASS）；物理 canvas @dpr2 = 480×560
  （断言 70，:416）；精灵绘制 `dh=224、dw=224×112/150≈167.25、x0=(240−167.25)/2≈36.37、y0=56`
  （断言 72，:422-424）。内容高容量 `118 × 224/150 = 176.2px ≈ 旧版 176`（断言 78
  `cellBox.h×display.h/cell.h≈176`，:446-447；旧目标常量 `WANT_H=176`：`petwork/tools/sprites.mjs:851`）。
  反例：cell 112×150 且**没有** display ⇒ 元素只剩 140×187.5（112×1.25 / 150×1.25），即小 42%。

## 规则 23：锚点 = 脚底中心；baselineY（像素行）优先于 anchor.y

- **现象**（不这么做时）：把锚点取 cell 底边（`anchor.y=1` ⇒ 像素行 150）时，角色脚底实际在
  baselineY=134 行，桌宠整体**上浮 (150−134)×1.4933 ≈ 23.9 CSS px**；缩放/拖动的位置基准也随之错。
- **根因**：cell 底边与脚底之间是打包留白（内容盒上下 ≥16px 余量，`sprites.mjs:29`；docs/03 §1），
  脚底行只有打包器知道——所以 meta 用 `baselineY` 像素行显式携带，引擎优先信它。
- **修法**：
  - `cellMeta()`：`aySrc = isNum(m.baselineY) ? m.baselineY : 比例换算的 anchor.y`
    （`plugin/src/pet.js:154`，注释原文「脚底基线优先取 baselineY（像素行）」）；
    anchor 双写法——值在 [0,1] 区间视为 cell 内比例，否则视为像素（:150-153，
    「锚在 0~1px 边缘的精灵不存在」）；clamp 进 cell 范围（:164-165）。
  - `geometry()`：锚点用**与绘制同一个系数** k=dh/ch 换算成元素内 px——
    `bx = x0 + ax×k`、`by = y0 + ay×k`（:383-384，注释原文「保证脚底像素级对准」）。
  - `layout()`：`stage.left/top = 脚底 px − bx/by`（:404-405），cfg.x/y（视口比例）记录的
    就是脚底中心（:373 节注释「几何：锚点 = 脚底中心」；footPx :386-389）。
  - 滚轮缩放只改 scale、不动 x/y：锚点是脚底 ⇒ 天然零漂移（:711-724，注释 :711-713）。
- **实测数字**：冒烟断言 71 硬算锚点——`bx = 120 = W/2`（anchor.x=0.5）、
  `by = (280−224) + 134×(224/150) = 256.107`（`tmp/pet-smoke.mjs:418-420`）；断言 132：
  内嵌/高清两套素材脚底恒钉在 `cfg.y = 0.82×800 = 656`（±1px，:785-789）。高清版
  baselineY=204、k=1（`dsh-pet-bg/assets/pet-hd.json:18`），by=56+204=260，脚底仍是 656。

## 规则 24：离屏预切 cell 缓存（buildCells），不在每帧对大图集算源矩形

- **现象**：每帧直接 `drawImage(大图集, 源矩形…)` 时，精灵出现 **1px 缩放抖动**。
- **根因**：源矩形坐标经缩放/锚点计算带小数，非整数源坐标在不同浏览器的取整不一致，
  帧与帧之间取整结果漂移（`pet.js:202-205` 注释原文：「避免每帧对大图集算源矩形时
  非整数源坐标在不同浏览器取整不一致，造成的 1px 缩放抖动」）。
- **修法**：图像 onload 后**一次性**把每个 cell 画到独立的 cell 尺寸小 canvas
  （`buildCells()`，:206-229；缓存 key = `"col,row"`，:225；预切时用整数源矩形
  `c*cm.cw, r*cm.ch`，:222），之后每帧只画小图（`drawStateAt` 取 `cells[f[0]+','+f[1]]`，
  :571-573）。内嵌加载（paintFrom onload，:237）与高清热切换（hdCommit，:264-265）各触发一次重建。
- **实测数字**：内嵌 8×21=168 格全预切（+1 可见 canvas = 新建 169 个，断言 80
  `tmp/pet-smoke.mjs:455`）；高清 8×40=320 格，会话 canvas 增量 489 = 168+320+1（断言 125，
  :772-773）。离屏内存（本机复跑打印行，公式 `cellCount×w×h×4B`：pet.js:267-269、
  sheetInfo.cellMemMB :1061）：高清 320×192×224×4B ≈ **52.5MB**、内嵌 168×112×150×4B ≈
  **10.8MB**，另图集本身解码 1536×8960×4B ≈ 52.6MB（:774；`dsh-pet-bg/README.md:176-178` 同数）。
  注意：:203 注释「图集是 8×5=40 个 cell」是历史残留（旧素材规格），当前两套图集实为 168/320 格。

## 规则 25：fps 每帧现算 ⇒ 改倍速立刻生效，不重排、不刷新

- **现象**：菜单点「加速」，动画速度**当帧**变化——不刷新页面、不重进状态、不重排布局。
- **根因**（机制，刻意设计）：fps 从不缓存。主循环每帧都调 `stateDef()`（tick :622、
  drawStateAt :562），`fps = CORE.clamp(meta.fps × fpsScale(), 0.2, 60)` 每次现算（:183）；
  帧序号由 `frameIndex()` 每帧从 `def.fps` 推（`i = floor(t/1000 × fps)`，:448；三角波 :449-453）。
  fps 只是时间参数、与几何无关 ⇒ 不需要 `layout()` 重排；`stepSpeed()` 写完配置只补一次
  即时重绘（:812-816）。单次动画（react）的时长同样每帧从现算 fps 推（:440）。
- **修法**：保持「现算、无缓存」；任何「把 fps 存起来」的优化都会让倍速改动延迟生效。
  注意 :774-775 注释里引的「pet.js:380/440」是旧行号，现已漂移至 :562/:622（本篇以实读为准）。
- **实测数字**（本机复跑，`tmp/pet-smoke.mjs:477-510` 的 measureGaps：可见 canvas 上 cell
  变化间隔，rAF 16ms 步长量化）：**idle 帧间隔 141.0→116.8ms**（fpsScale 1→1.2，经菜单点
  「加速」触发、无 reload，断言 86/87 :497-503）、**walk 123.8→88.6ms**（fpsScale 1→1.4，
  断言 88 :504-509）；即任务口径的 141→117 / 124→89。理论值 `1000/(fps×fpsScale)`：
  idle 7fps → 142.9→119.0ms、walk 8fps → 125.0→89.3ms，与实测在 ±16ms 量化内一致（输出行 :510）。

## 规则 26：fpsScale 的真默认值在 core.js 的 sanitize 里，pet.js 的兜底常量到不了

- **现象**（真实踩坑，`docs/08-踩坑清单.md:16` #10）：改 `pet.js` 的兜底常量 `DEF_FPS_SCALE`，
  实际默认播放速度纹丝不动。
- **根因**：配置读取链路是 `CORE.load()` → `sanitize()`（core.js:129-141，`cfg = sanitize(parsed)`
  :139；`set()` 写路径同样过 sanitize :179）。sanitize 的 pet 白名单**永远**把 `fpsScale`
  补成有限数：配置从未存过该值时，落到 `plugin/src/core.js:100` 的
  `clamp(pet.fpsScale, 0.15, 2, 1.4) : 1.4` ——**默认值在 core.js 注入**。因此 pet.js
  `fpsScale()` 里 `DEF_FPS_SCALE` 的两个用途（三目兜底与 clamp 兜底，:32-35）永远走不到；
  它实际只作用于 `resetSpeed()`（「速度」菜单项点击恢复默认，:817-820）和菜单文案（:778）。
  历史上 sanitize 的默认曾是 **0.6**（用户反馈「不流畅」后提速到 1.4——core.js:98-99 与
  pet.js:26-30 两处注释互相指认，pet.js:29-30 原文「那边才是配置里没存过 fpsScale 时实际生效的一处」）。
- **修法**：**改默认速度必须改 core.js:100**（clamp 兜底与 else 分支两处），并同步
  pet.js:31 的 `DEF_FPS_SCALE`（resetSpeed/文案用）；两处注释保持互相指认。现状核实：
  `pet.js:31 DEF_FPS_SCALE = 1.4`、`core.js:100` 默认 1.4——**两处一致，均为 1.4**。
- **实测数字**：两层钳位——存储/读取层 clamp **0.15~2**（core.js:100；pet.js:34），
  UI 按钮层钳 **0.4~2.0、步进 0.2**（`SPEED_STEP=0.2, SPEED_MIN=0.4, SPEED_MAX=2`，pet.js:811，
  注释原文「core sanitize 的 0.15~2 是存储层保护，保持不动」）。冒烟断言 89~95
  （tmp/pet-smoke.mjs:511-524）：存过 1.5 → 标签「速度 1.5×」（标签读实时配置）、
  加速 +0.2→1.7、上限钳 2.0、下限钳 0.4、点标签恢复默认 **1.4**、速度组与尺寸组互不串味
  （scale 仍=1）——本机复跑全 PASS。

## 规则 27：状态白名单 NAMES——不在里面的状态，菜单点了完全没反应

- **现象**（真实 bug，`docs/08-踩坑清单.md:15` #9）：素材里有 dead 状态（16 帧），
  右键菜单「报错装死」却**长期不可达**——点了完全没反应（实际是被静默改写成 idle），
  不报错、不提示。
- **根因**：`setState()` 对不在 `NAMES` 白名单里的状态名静默改写：`if (!NAMES[name]) name='idle'`
  （`plugin/src/pet.js:422`）；外挂 meta 校验也按 NAMES 计数（:305）。白名单缺项时，
  meta.states 带了该状态、菜单项也建了，点击链路照样在 setState 这一步被吞掉。
- **修法**：**新增状态必须同时改五处**（清单与 docs/08 #9 一致，行号为本仓库实读）：
  1. `NAMES`（pet.js:15，现 8 状态 `{idle,wait,walk,react,working,sleep,supervise,dead}`）；
  2. `stateDef()` 内置默认值（pet.js:171-179，如 dead 的 fps=8 在 :179）；
  3. `menuItems()` 菜单项（pet.js:749-756，「报错装死」在 :755）；
  4. `meta.states`（pet.json；生成端常量 `tools/pack_sheet.py:62-63, :67-70`——:61 注释原文
     指向 pet.js:15「不在里面的状态菜单点了没反应」；构建门槛 `plugin/tools/embed-sheet.mjs:44-52`
     要求至少六状态 idle/wait/walk/react/working/sleep，坐标越界即 die）；
  5. verify 标签断言（`plugin/tools/verify.mjs:141`，子串匹配清单含「报错装死/监工模式」，
     :138-140 注释原文「探针必须跟着 UI 改，否则是假失败」）。
  冒烟侧把 NAMES 从源码正则解析（`tools/smoke.mjs` 头注释 :17-18 设计意图；该文件并行编写中，
  不引其余行号），漏改任何一处都会 FAIL。
- **实测数字**：生产 meta 8 状态齐全、dead 16 帧（`petwork/out/pet.json:660-731, :870-883`）；
  冒烟断言 82.idle~82.dead 八状态 `setState` 全可达（tmp/pet-smoke.mjs:458-461）、
  85b「点报错装死 → dead 状态」（:472-473）——本机复跑 PASS。

## 规则 28：菜单项用素材文件夹名命名；非 idle 的模式自动关漫游

- **现象**（不这么做时）：手动选了动作，60 秒后被空闲漫游抢走——漫游自顾自进 walk/idle，
  用户的选择留不住。
- **根因**：漫游是「60s 无输入」驱动的后台行为（`IDLE_ROAM_MS=60000`，pet.js:22；tick 触发
  条件 `st.name==='idle' && p.roam && !p.locked && idleFor>60s`，:627；`startRoam()` 直接
  `enterState('walk')`，:511-518）。手动模式是用户显式指令，优先级必须更高。
- **修法**：右键菜单 8 个模式项**直接用素材文件夹名命名**（pet.js:749-756，实读核对）：
  待机眨眼=idle(:749) / 修bug=walk(:750) / 加载等待=wait(:751) / 敲代码=working(:752) /
  庆祝完成=react(:753) / 睡觉休息=sleep(:754) / 报错装死=dead(:755) / 监工模式=supervise(:756)
  ——与打包端组名映射 `DEFAULT_MAP` 完全同一张表（`tools/pack_sheet.py:65-66`）。
  `pickMode()`：除「待机眨眼」（roamOn=true，:749）外一律 `CORE.set({pet:{roam:false}})` +
  `stopRoam()`（:741-748；注释原文 :738-740「除『待机眨眼』外都会顺手关掉漫游，否则空闲漫游
  会把你手选的动作抢回 walk/idle」）。会话联动不受影响：来消息→wait、1.5s→working、
  完成→react 走 `force:true` 通道（`notify()` :458-478；`WORK_DELAY_MS=1500` :24）。
- **实测数字**：冒烟断言 85「点监工模式 → state=supervise 且 roam=false」（tmp/pet-smoke.mjs:470-471）、
  85c「dead/supervise 不被空闲漫游抢走（虚拟时钟推 60s 后仍 dead）」（:474-475）——本机复跑 PASS；
  working/wait 期间漫游/睡眠也不抢占（`busyLocked()` :418、tick :626）。verify.mjs:141 对
  8 个中文标签逐一子串断言。

## 规则 29：z-order 铁律——固定 z 阶梯 + body 直挂 + 绝不碰宿主层叠

- **现象**（历史真实事故，bg.js:3-5 注释原文）：给宿主容器写 position/z-index/filter/
  backdrop-filter 造出层叠上下文后，「宿主 z-index:1000 的设置弹窗就被压平（点不开）」；
  批量透明化后代元素（`*:not(...)` 一类全后代规则）会破坏宿主页面渲染（pet.js:5-6、bg.js:6-7 铁律注释）。
- **根因**：插件是宿主页面的客人，宿主的层叠关系不受它控制；给宿主容器造 stacking context
  会重排整棵子树的绘制顺序，全后代选择器则波及宿主自己的元素。
- **修法**（三条一起构成铁律）：
  1. **固定 z 阶梯**（数值实读）：`#dsh-pet-video` **z0**（背景视频层，bg.js:29）→
     `#dsh-pet-stage` **2147483000**（Z_STAGE，pet.js:16；CSS :885；召唤圆点 nudge 同层 :904-906）→
     `#dsh-pet-panel` **2147483001**（PZ，bg.js:11；CSS :31）→ `#dsh-pet-menu` **2147483002**
     （Z_MENU，pet.js:16；inline :828 + CSS :893）→ `#dsh-pet-compose` 派活输入框 **2147483003**
     （boot.js:364）。
  2. **浮层全部是 document.body 直接子节点**（pet.js:5 铁律注释）：stage/nudge
     （pet.js:928, :931）、video 层/panel（bg.js:312-315，注释原文「都是 body 直接子节点（§2）」）、
     composer（boot.js:325）。
  3. **样式只写 `#dsh-pet-*` 前缀选择器**，绝不写全后代透明规则；毛玻璃滤镜只加在面板自己身上
     （bg.js:6-7 注释原文、:27-41 CSS；pet.js injectCss :882-911 节注释「只出现 #dsh-pet-* 前缀，
     绝不碰宿主容器」；样式槽位隔离注入 head：core.js:372-382）。
- **实测数字**：无头 Edge 验收 **60 PASS / 0 FAIL**、零 console.error——验收页刻意复刻
  「设置弹窗 z=1000 嵌在 overflow:hidden 列里 + 对话区 sticky z=5」这个曾让前代翻车的结构，
  断言遮罩仍 `rgba(0,0,0,.24)`、弹窗中心命中测试落在弹窗内、`_sidebarCol`/`_frame` 未被插件加
  z-index/filter（`dsh-pet-bg/README.md:130-136`）。
- **备注（注释与数值矛盾，以数值为准）**：bg.js:11 注释写「面板浮在桌宠/菜单之上」、

## 尺寸不变量 k = display / cell：验收必须同时断言元素尺寸和内容 CSS px

**显示尺寸的不变量是「屏幕上的 CSS px」，不是「cell 内的 px」。** 引擎侧公式：
`k = dspH / ch`（`sheetInfo()`，pet.js:1042），内容上屏 `contentCssW/H = source.cellBox × k`
（:1059-1060）；:1031-1034 注释原文「这个数在两套素材间必须一致（146×176），否则桌宠会
悄悄变大变小」。控制台随时可查：`__DSH_PET_BG__.PET.sheetInfo()`。

| | 内嵌模式 | 高清模式 |
|---|---|---|
| cell | 112×150（pet.json:4-7） | 192×224（pet-hd.json:4-7） |
| display | 192×224（pet.json:10-13） | 192×224（pet-hd.json:10-13） |
| **k = display.h/cell.h** | 224/150 = **1.4933** | **1** |
| 内容盒 cellBox | 98×118（pet.json:765-768） | **146×176**（pet-hd.json:1393-1396，按 k 反算） |
| 内容上屏 CSS px | 98×1.4933≈146.3，118×1.4933≈176.2 → **146×176** | 146×1 = **146×176**（一致 ✓） |
| 元素尺寸（display×scale×PAD） | **240×280** | **240×280**（相同） |

- 内容**宽**也用同一个 k：绘制宽 `dw = dh×(cw/ch)`（pet.js:380）⇒ 宽高同为 1.4933 倍；
  `display.w=192` 只决定元素盒宽 W=240，精灵实绘宽 167.25 居中（:381-382），
  所以 146 而不是 98×192/112=168。（打包端打印的 kw/kh 是「内容盒**容量**上限」口径，
  见 `tools/pack_sheet.py:183-187` 与 docs/03 §5。）
- **直觉错法**：高清内容盒按 cell 等比放大取 **168×200**（98×192/112=168；历史记录原文
  「不是按 cell 比例放大的 168×200」，`dsh-pet-bg/README.md:166-167`）⇒ 内容高
  **200/176 = +13.6%**，桌宠悄悄变大。
- **为什么只比元素尺寸抓不出**：元素尺寸完全由 display 决定（geometry :381），两种模式的
  display 都是 192×224 ⇒ 元素 style 尺寸**都仍是 240×280**（断言 126 硬断言高清模式
  `style.width==='240px'`，tmp/pet-smoke.mjs:775-776）——内容盒错了它照样对。
  **结论：验收必须同时断言「元素尺寸」和「内容的屏幕 CSS px」。**
- 守这条不变量的断言（本机复跑全 PASS）：断言 100「两套素材的内容屏幕 CSS px 一致
  （±0.5px）」（:557-562）、断言 127「高清内容容量 ≈146×176（±0.6px）」（:777-778）、
  断言 132「两模式零跳变：元素 240×280 相同 + 内容 CSS px 差 <0.6px + 脚底仍钉在 656」
  （:785-789）。高清构建命令直接烧入反算值 `--box-w=146 --box-h=176`
  （`dsh-pet-bg/README.md:156`）。本仓库 `tools/smoke.mjs` 按同一设计：一切几何期望从传入
  meta 推导，240×280 仅在 `meta.display==192×224` 时作为条件锚点断言（头注释 :19-20；
  该文件并行编写中，行号以当前版本为准）。构建验收流程见 docs/06；打包侧同一推理见 docs/03 §5。
